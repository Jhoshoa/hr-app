# Supabase Auth And Local Postgres Development Strategy

Created: May 13, 2026.

## Context

For local development, the application currently uses Docker Postgres for the business database. Prisma connects to that database through `DATABASE_URL`.

Supabase is currently used as the external authentication provider. The backend verifies bearer tokens with Supabase Auth, then stores and reads the application user, tenant memberships, roles, permissions, employees, and audit data from the Prisma database.

This means Supabase Auth and the application database are related, but they are not the same source of truth.

## Current Backend Flow

The expected request flow is:

1. The frontend signs the user in with Supabase Auth.
2. Supabase Auth returns a session with an access token.
3. The frontend sends API requests with `Authorization: Bearer <access_token>`.
4. The API verifies the token through the configured auth provider.
5. The API receives an external user identity from Supabase.
6. The API looks for a local `User` using `externalAuthProvider` and `externalAuthUserId`.
7. If the local user does not exist, the API creates it.
8. The API resolves tenant memberships, roles, and permissions from local Postgres.

The local `User` table is not replacing Supabase Auth. It is the local application identity record. Supabase owns login, OAuth, password/session lifecycle, and token issuance. The application owns tenant access, roles, employee linkage, audit history, and business data.

## How Users Are Related

Supabase Auth has its own user ID. The local app stores that value in:

```text
User.externalAuthProvider = "supabase"
User.externalAuthUserId = Supabase auth user id
```

When a user logs in with Google, Supabase creates or resolves a Supabase Auth user. The backend then maps that external identity into the local `User` table.

Example:

```text
Supabase Auth user:
  id: 3f8b...
  email: person@example.com
  provider: google

Local app user:
  id: local uuid generated by Prisma
  email: person@example.com
  externalAuthProvider: supabase
  externalAuthUserId: 3f8b...
```

The local `User.id` is what the HR app uses for tenant memberships, employee ownership, audit events, and permissions. The Supabase ID is only the bridge back to the external auth system.

## Supabase Auth Users Vs Local App Users

Supabase Auth maintains its own user records. In a Supabase-hosted project, those records live in Supabase Auth's managed schema, commonly exposed as `auth.users`.

Our local `User` table is intentionally separate. It should not store passwords, password reset state, refresh tokens, OAuth provider internals, or email confirmation state. Those belong to Supabase Auth.

The split should be:

| Data | Source of truth |
|---|---|
| Email/password credentials | Supabase Auth |
| Google OAuth identity | Supabase Auth |
| Password reset flow | Supabase Auth |
| Email confirmation | Supabase Auth |
| Auth sessions and refresh tokens | Supabase Auth |
| Application user ID | Local `User` table |
| Tenant memberships | Local Postgres |
| Roles and permissions | Local Postgres |
| Employee profile linkage | Local Postgres |
| Audit events | Local Postgres |

Having both tables is not a problem as long as the boundary is clear:

```text
Supabase auth user id -> User.externalAuthUserId
Supabase auth provider -> User.externalAuthProvider
Local app user id -> User.id
```

The backend should never join directly against Supabase's internal `auth.users` table in normal application code. It should treat Supabase Auth as an external identity provider and use the verified token or admin API response to map into the local `User`.

This keeps the app portable. If we later move from local Docker Postgres to Supabase Postgres, the same separation still works. If we later replace Supabase Auth with another provider, the local business tables can remain mostly unchanged because they depend on `User.id`, not on provider-specific auth tables.

## Roles, Permissions, And JWT Claims

Supabase JWTs include auth-level claims such as the Supabase user id, email, audience, expiration, and the Supabase database role such as `authenticated`, `anon`, or `service_role`.

That built-in JWT `role` is not the same thing as our application roles. In Supabase, `authenticated` means "this request belongs to a signed-in user" for Supabase APIs and Row Level Security. It does not mean "HR admin", "manager", "employee", or any tenant-specific role in this application.

Our application roles and permissions currently live in local tables:

```text
Role
Permission
RolePermission
TenantMembership
```

For this app, the recommended model is:

1. Supabase Auth proves who the user is.
2. The backend maps the Supabase user id to local `User`.
3. The backend loads tenant membership, role, and permissions from local Postgres.
4. The backend authorizes each request using local application data.

This means we do not need Supabase to generate JWTs containing every app permission for the first implementation.

Supabase does support custom claims through access-token hooks. That can be useful when Supabase Postgres Row Level Security needs role or permission data inside `auth.jwt()`. However, custom claims are generated when a token is issued or refreshed, so permission changes may not be reflected until the client gets a new access token.

Because this app already has a NestJS API as the authorization boundary, local permission lookup is safer and simpler for now:

- Permission changes can take effect on the next API request.
- Tenant-specific roles do not bloat the JWT.
- We avoid synchronizing local role tables into Supabase Auth metadata.
- We keep local Docker Postgres development aligned with production behavior.

Use JWT custom claims later only if we expose business tables directly through Supabase APIs or if we move authorization into Supabase Row Level Security policies.

## Can We Simulate Supabase Auth Locally?

Yes, but it should be limited.

A fake local auth provider can be useful for backend unit tests, e2e tests, or fast development without internet access. It could accept a local development token and return a fixed external user object.

However, it is not a good replacement for testing Google login. Google OAuth involves browser redirects, Supabase callback handling, session creation, refresh behavior, and provider-specific metadata. A fake provider would not catch problems in that flow.

Recommended split:

- Use a fake auth provider only for automated tests or isolated backend development.
- Use real Supabase Auth for manual login testing and frontend integration.
- Keep the business database local through Docker Postgres while testing real Supabase Auth.

## Recommended Local Development Approach

Use this setup for normal development:

```text
DATABASE_MODE=local
DATABASE_URL=postgresql://hr_app:hr_app_password@localhost:5434/hr_app?schema=public
AUTH_PROVIDER=supabase
SUPABASE_URL=<real Supabase project URL>
SUPABASE_ANON_KEY=<real anon key>
SUPABASE_SERVICE_ROLE_KEY=<real service role key>
```

This gives the best tradeoff:

- Google login is real.
- Supabase token verification is real.
- Business data stays in local Docker Postgres.
- Local migrations and seed data stay fast and disposable.
- We do not depend on Supabase Postgres for day-to-day feature development.

Later, if needed, the database can be switched explicitly:

```text
DATABASE_MODE=supabase
DATABASE_URL=<Supabase Postgres connection string>
```

The important part is that database mode and auth provider should be separate concepts. Supabase Auth can be real while the database remains local.

## Frontend Login Flow

The frontend should implement these basic views first:

1. Login page.
2. Auth callback page.
3. Authenticated shell or dashboard placeholder.
4. Logout action.

The login page should call Supabase sign-in with Google and pass a callback URL controlled by frontend environment config.

The callback page should let the Supabase client read the returned session, then redirect the user into the app. After that, the frontend should call the backend `/me` endpoint with the Supabase access token.

Expected frontend sequence:

```text
User clicks "Continue with Google"
  -> Supabase redirects to Google
  -> Google redirects back to Supabase
  -> Supabase redirects to the frontend callback URL
  -> Frontend reads the Supabase session
  -> Frontend calls GET /api/me with Bearer token
  -> Backend creates or resolves local User
  -> Backend returns user and tenant memberships
  -> Frontend routes to the selected tenant workspace
```

## Backend Implications

The backend already has the core shape for this:

- `AuthGuard` extracts the bearer token.
- `SupabaseAuthProvider` verifies the token and reads the Supabase user.
- `ResolveAuthenticatedUserUseCase` finds or creates the local `User`.
- `PrismaUsersRepository` stores `externalAuthProvider` and `externalAuthUserId`.
- `MeController` returns the local user context and available tenants.

The main missing piece is tenant bootstrap. A newly created local user may not have a `TenantMembership`, so `/me` can return a user with an empty `tenants` array.

For early development, choose one of these bootstrap strategies:

1. Seed a known Supabase user ID into local Postgres.
2. Add a development-only script that links a local user to the demo tenant after first login.
3. Add an admin invitation flow later, once auth and tenant management screens exist.

The best short-term option is the second one. Let the backend create the local user on first authenticated request, then run a small local script or endpoint to attach that user to the demo tenant and role.

In production, this should become an explicit onboarding or invitation flow. A new Supabase Auth user should not automatically receive access to a tenant unless the product rules say that self-signup is allowed for that tenant.

Recommended production behavior:

1. User authenticates with Supabase Auth.
2. Backend resolves or creates local `User`.
3. Backend checks local `TenantMembership`.
4. If no membership exists, return an onboarding, pending access, or no-tenant state.
5. Tenant access is granted by invitation, admin assignment, or a controlled self-signup rule.

## Environment Variables To Add Later

The current repo uses `DATABASE_URL` directly. To make behavior more explicit, add:

```text
DATABASE_MODE=local
LOCAL_DATABASE_URL=postgresql://hr_app:hr_app_password@localhost:5434/hr_app?schema=public
SUPABASE_DATABASE_URL=
AUTH_PROVIDER=supabase
AUTH_MODE=supabase
```

Suggested meaning:

| Variable | Purpose |
|---|---|
| `DATABASE_MODE` | Selects `local` or `supabase` database mode. |
| `LOCAL_DATABASE_URL` | Docker Postgres connection string. |
| `SUPABASE_DATABASE_URL` | Supabase Postgres connection string, only used when database mode is `supabase`. |
| `AUTH_PROVIDER` | Selects the auth provider implementation. |
| `AUTH_MODE` | Allows `supabase` for real auth and optionally `mock` for local-only tests. |

Do not use a single variable like `USE_SUPABASE=true`, because Supabase can mean Auth, database, storage, realtime, or edge functions. Each concern should be explicit.

## Testing Strategy

Use three levels of testing:

### Unit Tests

Mock the auth provider. These tests should not call Supabase.

Validate:

- Token identity is mapped into local users.
- Existing users are reused.
- New users are created from external identity.
- Tenant memberships control access.

### Backend E2E Tests

Use a fake auth provider or test-only token verifier. These tests should focus on API behavior, not Google OAuth.

Validate:

- Protected routes reject missing tokens.
- Protected routes accept valid test identities.
- `/me` returns the expected user and tenants.
- Tenant context and permissions are enforced.

### Manual Frontend Auth Testing

Use real Supabase Auth with Google.

Validate:

- Login redirects correctly.
- Callback page receives a session.
- Frontend stores or reads the current session correctly.
- API requests include the bearer token.
- Backend creates or resolves the local user.
- `/me` returns the expected tenant access.

## Recommended Next Steps

1. Keep Docker Postgres as the default business database for local development.
2. Configure a real Supabase project for Auth and Google OAuth.
3. Create frontend `login` and `auth/callback` pages.
4. Add frontend Supabase client configuration.
5. Call `/me` after callback/session restoration.
6. Add a local bootstrap path to attach the first logged-in user to the demo tenant.
7. Later, add explicit `DATABASE_MODE` and `AUTH_MODE` handling in backend configuration.

## Decision

Do not try to fully replace Supabase Auth locally for normal development.

Use real Supabase Auth for browser login and Google OAuth, while keeping the application database local in Docker Postgres. This gives realistic authentication behavior without forcing all business data into Supabase Postgres during early development.
